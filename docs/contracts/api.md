# Initial API and event contracts

Design baseline 2026-11-08. Base `/api/v1`, JSON UTF-8, same-origin HTTPS.
OpenAPI 3.1 will be generated by FastAPI/Pydantic, with the TypeScript client
generated from that artifact. No manually maintained duplicate domain DTOs.
This document establishes behavior before implementation; routes below are
planned, not proof of deployed endpoints.

## Common types, authorization and concurrency

UUID: canonical UUID string, never example placeholders in fixtures. Instant:
RFC3339 with explicit offset, normalized to UTC. Date: YYYY-MM-DD.
Priority: low/medium/high/critical. Unknown input properties are rejected.
Null explicitly clears a nullable field; absent PATCH property preserves it.
All body strings are bounded; initial description/comment cap 64 KiB UTF-8.
Titles/subjects are 1..300 characters after validation. Limits are product
defaults subject to a reviewed change, not unlimited database fields.

Cookie session is required except health and session creation. All writes also
require a session-bound CSRF token and Origin verification. A route's named
permission is combined with client and resource predicates in the RBAC design.
Out-of-scope IDs return 404 without names; authenticated known-scope forbidden
actions return 403; anonymous API requests return 401. No redirect-to-HTML API error.

`GET` collection query: limit integer 1..100 (default 50), opaque cursor,
allowlisted filters and sort. Response `{items: T[], next_cursor: string|null}`.
Cursor binds sort/filter hash and uses last stable tuple + UUID tie-breaker.
Changed filters reject a mismatched cursor with 422. Pagination is live rather
than snapshot isolation; concurrent edits may change membership. Queries
parameterize user text and apply policy predicates before aggregation/FTS.

Mutable detail returns `version` and `ETag: "<version>"`. PATCH, transitions
and destructive mutations require `If-Match`; absent 428, stale 409. Update
predicate checks version in the database, increments once and audits atomically.
JSON errors use `application/problem+json`:

```json
{
  "type": "urn:altvia:problem:version-conflict",
  "title": "Resource changed",
  "status": 409,
  "code": "version_conflict",
  "correlation_id": "request-correlation-value",
  "errors": []
}
```

Validation uses 422 with field paths and safe reasons, malformed JSON 400,
oversize 413, unsupported media 415, rate limit 429 with Retry-After.
Do not echo passwords, message bodies or foreign resource IDs in errors.

Critical POSTs require `Idempotency-Key` (1..128 printable safe characters).
Persist namespace `(actor, route, key)`, request canonical hash and outcome in
the same transaction. Same hash replays 200 with original resource ID;
different hash returns 409. Concurrent key claim waits or returns safe conflict.
Keep API keys for at least 7 days; business unique keys remain indefinitely
while the business record exists. Expiry never permits duplicate email/task
effects. A failed rolled-back validation does not consume the key.

## Identity and configuration

| Method and suffix | Request/response | Permission and effect |
| --- | --- | --- |
| GET `/health/live`, `/health/ready` | Minimal `{status}`; readiness 503 when DB unavailable | Anonymous, no version/config/secret disclosure |
| POST `/auth/sessions` | `{email,password}`; 201 `{user,expires_at,csrf_token}` + secure cookie | Generic auth failure 401; rate controlled; no idempotency header on credential login |
| GET `/auth/me` | `{id,display_name,email,capabilities,csrf_token}` | Current user only, no password_hash/session token |
| DELETE `/auth/sessions/current` | 204; revoke cookie/session | CSRF, current user; idempotent |
| GET/POST `/users`, PATCH `/users/{id}` | Account status/profile only; password setup through separate one-time flow | identity.manage; no arbitrary role escalation |
| GET/POST `/teams`, `/teams/{id}/members` | Named team and validated internal user IDs | identity.manage or scoped team administration |
| POST/DELETE `/role-bindings` | Exact role and scope fields from data model | platform identity admin; audited, never self-grant through profile PATCH |

Bootstrap administrator and password reset use a one-time restricted management
command, not public signup. No default user/password fixture in production.
Password update/reset revokes all sessions and increments auth_version.
Phase 1C-a also provides restricted CLI create-user, enable-user, disable-user,
grant-admin and revoke-admin. These are host/DB management operations, not the
planned HTTP administration routes above. State/privilege changes are atomic,
revoke prior sessions and preserve at least one active platform administrator.
No-op requests create no repeated audit/outbox effect. Platform administration
does not confer customer-content access. See the development runbook for commands.

### Phase 1C-k account administration contract

ADR-0016 supersedes the planned generic profile/role HTTP rows for this delivered
increment. GET /users keeps its summary shape. POST /users creates an ordinary
active account; GET /users/{id} returns the public administrative snapshot.
POST /users/{id}/activation, /password, /platform-admin and /team-roles expose
only the corresponding management operation. GET /users/{id}/team-roles returns
a bounded account-scoped binding page. Exact request/response models are generated
in openapi.json. No profile PATCH or arbitrary role-binding endpoint is implemented.

All require fresh identity.manage. Writes acquire the identity lock before session
authentication, check exact Origin/CSRF and require Idempotency-Key; existing-account
writes also require the reviewed If-Match. User.auth_version is the public version.
Every security change invalidates sessions, advances version and atomically records
attributed audit/outbox; no-ops preserve sessions/version. Last-active-admin and
inactive-account/team grant checks remain in the management service.

Credential receipts fingerprint canonical payloads with scoped Argon2id, never a
fast password verifier. Results contain public fields only. Replays reauthorize
and return the historical receipt without reapplying the effect. A fresh self
mutation clears the cookie and returns X-Session-Revoked:true; that header is never
stored or replayed. The browser refetches current state before further writes.

### Phase 1C-b team administration contract

ADR-0009 distinguishes identity team metadata from operational/client content.
All routes in this slice require current identity.manage; membership alone grants
none. GET /users returns bounded internal summaries {id,display_name,email,active}
for selecting an existing account, without password/session/role details.

Team response: {id,name,active,version,created_at,updated_at}. POST /teams accepts
{name}; PATCH /teams/{id} accepts a nonempty subset of {name,active}. Names are
trimmed, 1..150 characters; unknown fields are forbidden. Archive preserves
roster/history. No hard delete. GET detail/PATCH returns ETag: "<version>".

GET /teams/{id}/members lists active roster entries {user_id,display_name,
account_active}. POST accepts {user_id}, requires an active team/account, returns
201 {team_id,user_id,team_version}, or 200 when already present without change.
DELETE /teams/{id}/members/{user_id} marks membership inactive, returns 204 and
the team's current ETag. An absent/inactive membership is a no-op with a current
If-Match. Each real change increments the team once and appends audit/outbox
atomically. PATCH and roster writes require the team If-Match; no-op retains it.

Critical POSTs require a 1..128-character Idempotency-Key using letters, digits,
period, underscore, colon or hyphen. The hash includes normalized body and the
membership If-Match. Matching replay returns the original result with 200 after
fresh authorization, even if that result's version is now historical. Refetch
before another edit. Different hash: 409. Failed validation/version checks do
not consume a new key. Records persist at least seven days; no purge/reuse job.

Lists use limit 1..100 (default 50), fixed ascending UUID order and opaque cursor
bound to users, teams or that team's member list. Invalid/cross-route cursors
and unsupported query parameters return 422. No filters/sort parameter in this
bounded slice. Writes accept small
JSON bodies only, bounded before parsing. Authentication failures and Origin/CSRF
errors follow the common contract; private responses are no-store.

### Phase 1C-c persisted team read delegation

ADR-0010 extends team metadata reads to explicit viewer/operations_manager team
bindings. Global identity.manage still governs /users and every team/roster write.
Scoped-only readers can list/get only bound teams and read those rosters; SQL
scope predicates apply before pagination. No read grant returns403; an unbound
team ID requested by a scoped reader returns404 without names or member details.
Archive preserves an existing explicit read grant. Revocation removes it and
invalidates old sessions. Ordinary roster membership remains insufficient.

Restricted CLI grant-team-role/revoke-team-role uses --email, --team-id and the
fixed --role viewer|operations_manager, with typed account/scope confirmation.
Grant requires active account/team; revoke remains possible after inactivation.
No client content, identity.manage, arbitrary role or HTTP grant mutation is
created by this interface. Global auth capability output remains unchanged.

## Domain resource schemas

### Work item core (ADR-0020)

This slice adds real /api/v1/work-items and project work-candidates, with the
strict WorkCreate/WorkPatch/Transition schemas in generated OpenAPI. GET collection
requires project_id, UUID cursor and limit 1..100/default50. All reads reuse the
actual project scope, never team metadata or global administration. The page's
can_create/can_manage describe role authority independently of pagination;
project_writable separately describes current project/customer/team availability.

Creation uses Idempotency-Key and returns only {work_item_id,project_id}.
PATCH requires If-Match and cannot alter status/work_type/project_id. Transition
and comment POSTs require both If-Match and Idempotency-Key. Current authority
is checked before replay; saved effects ignore later version/reference changes
without repeating the mutation. Transition replay retains its recorded version
but refreshes authority/availability flags; clients refetch current state.
New work mutations require active project/customer/team. Candidates are active
manager/agent contributors with current scope; no account emails are returned.
Only managers assign/reparent; agents create self-owned work and edit/transition
only current owned/participating work. Assignment is never a grant.

GET detail returns ETag, plain text, owner_name and linked assignees (IDs/display
names), precise due data and current capability flags. Names come from actual
assignment links, including former contributors, not an unrestricted directory.
GET comments is chronological by created_at/ID and has a scoped timestamp cursor.
GET status-history is immutable, descending version order with scoped version
cursor, and includes original transition reasons. GET activity uses existing
scoped descending timestamp/event-ID pagination. Bodies/reasons never enter the
worker's safe event payload. Parent and assignment changes are atomic with task
version/audit/outbox; no parent-child state cascade or ticket state coupling.

Date-only deadlines retain the source date/zone and exclusive next-local-day
boundary. PostgreSQL validates known zones and rejects skipped dates. Numeric
epoch coercion is rejected; instant precision requires an aware ISO timestamp.
No recurrence, dependency graph, Kanban, FTS, My Work or import is supplied by
this task-core slice. Complete-product routes below remain separate contracts.

### Project milestone extension (ADR-0024)

Phase 2G adds /projects/{project_id}/milestones. Scoped GET collection returns
items/next_cursor/project_writable, SQL UUID paging bound to actor and parent,
limit1..100/default50 and no counts. POST accepts strict {title,due?}, Origin/CSRF
and Idempotency-Key; receipt201/replay200 is only {project_id,milestone_id} after
fresh project management. A committed replay never changes current state.

GET /projects/{project_id}/milestones/{milestone_id} returns scoped fields, own
version/ETag, can_manage and project_writable. PATCH there accepts strict nonempty
{title?,due?,state?}, milestone If-Match, nullable due only; it returns current
record/ETag. States planned/done/cancelled require reopening to planned before
switching between terminal states. Dates/instants reuse existing work semantics.
Actual writes require active project/team/customer, advance milestone and Project
versions, and emit redacted project-bound milestone activity. No-op/replay preserves
existing versions/state after archival; no delete or task synchronization.
Source/runtime tests are recorded separately from deferred final target homologation.

### Project member administration extension (ADR-0023)

Contracts selected before implementation. POST /projects/{id}/members accepts
strict {email,role_name}, Project If-Match and Idempotency-Key. Normalize email
using identity policy; resolve only inside the authorized mutation. Return minimal
{project_id,user_id}, 201/new intent or 200/committed replay. No account discovery
endpoint or global account listing is granted. Every replay rechecks current
project management and parses If-Match before returning the original IDs; it never
regrants or supplies current member state. Fresh POST compares Project version.

PATCH /projects/{id}/members/{user_id} accepts strict {role_name} and Project
If-Match; DELETE at the same path requires Project If-Match. Both return204 and
current Project ETag. PATCH requires an existing membership/binding half; DELETE
of an absent pair is a no-op without global account resolution. Roles are
viewer|agent|project_manager. Actual changes atomically update both records,
invalidate target sessions, advance Project and emit project.access_changed.
No-ops preserve versions/sessions/events even with inactive references. Actual
grants require active account/project/client and an existing customer ceiling.
Unknown/inactive/customer-ineligible add targets share422 invalid_project_member.
Self-removal/demotion ends the current session; inherited client authority remains
independent. The existing CLI remains available for last-manager recovery.
Member pages additionally return project_version, checked unchanged around the
roster query; concurrent changes return409. This pairs the reviewed membership
state with its write precondition without locking projects after authentication.

## State transitions and temporal semantics

Phase3D private-note and queue note_access contracts are defined by ADR-0029.
GET/POST `/tickets/{id}/notes` and scoped GET `/tickets/{id}/notes/{note_id}`
enforce note.read/write independently of ticket scope. Strict plain-text protected
writes return immutable ticket/note IDs. Member writes accept optional note_access
none|read|write, preserving legacy omission/fingerprints and compatible grants.
Ticket output adds can_read_notes/can_add_note. Ordinary activity filters private
note events before pagination. Public reply/transport contracts follow separately.

Work: todo -> in_progress/blocked/cancelled; in_progress -> blocked/done/cancelled;
blocked -> todo/in_progress/cancelled; done -> in_progress (explicit reopen);
cancelled -> todo (manager restore). Initial ongoing work enters in_progress;
finishing it requires explicit end-of-operation, does not generate recurrence.
Leaving blocked clears current blocked reason but preserves history.

Ticket: new -> open; open -> pending_customer/pending_third_party/resolved;
pending states -> open/resolved; resolved -> closed/open; closed -> open only
by authorized reopen policy. Reopening creates a new SLA cycle with preserved
previous cycle. Closure/reopen authorization and configured grace period are
policy inputs, not hardcoded SLA promises. Idempotent same-state replay is not
a new transition/event. A public customer message can reopen under configured
policy; a private note cannot satisfy first response or customer communication.

Task deadline category order: completed/cancelled (report separately), ongoing,
no_due_date, overdue, due_soon (0..3 local days), on_track. Date-only overdue
starts at the following local midnight. Instant deadlines compare real instants.
No due date is fabricated from SLA, creation date or calendar views.

## My Work and analytics

Response items: `{kind: work_item|ticket, id, title, status, priority, due,
origin, linked_tickets: [{id,number,status}], version}`. Restrict related fields
to the caller's ACL. Tasks qualify through owner or explicit assignee membership;
tickets through assignee. ADR-0007 defines N:N suppression. Deduplication takes
place before cursor pagination across the full filtered authorized set.
Response also names `as_of`, timezone and applied filters. `unified_count`,
`ticket_count`, `work_item_count`, `active_no_due_date_count` and
`all_missing_deadline_count` have distinct meanings. Counts are optional on
paginated reads; when provided they use the same predicates/projection.

## Durable event contract

Envelope: event_id UUID, event_type allowlisted string, schema_version positive
integer, aggregate {type,id,version}, occurred_at UTC, actor {type,id nullable},
correlation_id, causation_id nullable, payload bounded typed object. Payload
uses IDs and transition information, not full email bodies or credentials.

Initial events: ticket.created/assigned/status_changed/message_received,
work_item.created/assigned/blocked/completed, sla.breached. Aggregate mutation
and envelope commit together. Consumer re-reads authoritative resource/scope
and never treats serialized actor as an unrestricted authorization grant.

`ticket.assigned` payload contains ticket_id, old_assignee_id nullable,
new_assignee_id, queue_id, client_id and aggregate version. Automation execution
records rule revision and source event. Stable logical effect key remains
`(rule_id, action_id, ticket_id)` across rule edits/reassign/reopen unless a
separate authorized new-work operation intentionally creates another task.
Each action has an immutable server-assigned UUID. Reordering preserves its
identity; deletion tombstones it; replacement creates a new UUID and requires
explicit review of new-work effects. Never reuse action IDs or infer identity
from position. Existing execution history retains the original rule revision.
