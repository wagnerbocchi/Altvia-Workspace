# Initial API and event contracts

Design baseline 2026-11-08. Base `/api/v1`, JSON UTF-8, same-origin HTTPS.
OpenAPI 3.1 will be generated by FastAPI/Pydantic, with the TypeScript client
generated from that artifact. No manually maintained duplicate domain DTOs.
This document establishes behavior before implementation; routes below are
planned, not proof of deployed endpoints.

## Common types, authorization and concurrency

UUID: canonical UUID string, never example placeholders in fixtures. Instant:
RFC3339 with explicit offset, normalized to UTC. Date: YYYY-MM-DD.
Priority: low/medium/high/critical. Unknown input properties are rejected.
Null explicitly clears a nullable field; absent PATCH property preserves it.
All body strings are bounded; initial description/comment cap 64 KiB UTF-8.
Titles/subjects are 1..300 characters after validation. Limits are product
defaults subject to a reviewed change, not unlimited database fields.

Cookie session is required except health and session creation. All writes also
require a session-bound CSRF token and Origin verification. A route's named
permission is combined with client and resource predicates in the RBAC design.
Out-of-scope IDs return 404 without names; authenticated known-scope forbidden
actions return 403; anonymous API requests return 401. No redirect-to-HTML API error.

`GET` collection query: limit integer 1..100 (default 50), opaque cursor,
allowlisted filters and sort. Response `{items: T[], next_cursor: string|null}`.
Cursor binds sort/filter hash and uses last stable tuple + UUID tie-breaker.
Changed filters reject a mismatched cursor with 422. Pagination is live rather
than snapshot isolation; concurrent edits may change membership. Queries
parameterize user text and apply policy predicates before aggregation/FTS.

Mutable detail returns `version` and `ETag: "<version>"`. PATCH, transitions
and destructive mutations require `If-Match`; absent 428, stale 409. Update
predicate checks version in the database, increments once and audits atomically.
JSON errors use `application/problem+json`:

```json
{
  "type": "urn:altvia:problem:version-conflict",
  "title": "Resource changed",
  "status": 409,
  "code": "version_conflict",
  "correlation_id": "request-correlation-value",
  "errors": []
}
```

Validation uses 422 with field paths and safe reasons, malformed JSON 400,
oversize 413, unsupported media 415, rate limit 429 with Retry-After.
Do not echo passwords, message bodies or foreign resource IDs in errors.

Critical POSTs require `Idempotency-Key` (1..128 printable safe characters).
Persist namespace `(actor, route, key)`, request canonical hash and outcome in
the same transaction. Same hash replays 200 with original resource ID;
different hash returns 409. Concurrent key claim waits or returns safe conflict.
Keep API keys for at least 7 days; business unique keys remain indefinitely
while the business record exists. Expiry never permits duplicate email/task
effects. A failed rolled-back validation does not consume the key.

## Identity and configuration

| Method and suffix | Request/response | Permission and effect |
| --- | --- | --- |
| GET `/health/live`, `/health/ready` | Minimal `{status}`; readiness 503 when DB unavailable | Anonymous, no version/config/secret disclosure |
| POST `/auth/sessions` | `{email,password}`; 201 `{user,expires_at,csrf_token}` + secure cookie | Generic auth failure 401; rate controlled; no idempotency header on credential login |
| GET `/auth/me` | `{id,display_name,email,capabilities,csrf_token}` | Current user only, no password_hash/session token |
| DELETE `/auth/sessions/current` | 204; revoke cookie/session | CSRF, current user; idempotent |
| GET/POST `/users`, PATCH `/users/{id}` | Account status/profile only; password setup through separate one-time flow | identity.manage; no arbitrary role escalation |
| GET/POST `/teams`, `/teams/{id}/members` | Named team and validated internal user IDs | identity.manage or scoped team administration |
| POST/DELETE `/role-bindings` | Exact role and scope fields from data model | platform identity admin; audited, never self-grant through profile PATCH |

Bootstrap administrator and password reset use a one-time restricted management
command, not public signup. No default user/password fixture in production.
Password update/reset revokes all sessions and increments auth_version.

## Domain resource schemas

| DTO | Required create fields | Optional/derived response fields |
| --- | --- | --- |
| Client | name | active, default_project_id; id/version/timestamps server owned |
| Project | name, scope_kind, team_id; client_id iff client | operational_area_id; membership managed separately |
| WorkItem | project_id, title, priority, work_type | description, parent_id, owner_id, assignee_ids, due {precision,date,timezone} OR {precision,instant}; server status defaults todo |
| Ticket | client_id, requester_id, queue_id, subject, priority | category_id, description, assignee_id; status new, number/source/version server owned |
| TicketMessage | visibility, body_text | body_html input sanitized; public requires explicit recipient contact IDs, internal forbids recipients |
| WorkLink | existing_work_item_id OR create_work_item | relation_type implements/related; mutually exclusive payloads |
| Transition | target_status, reason when required | work ongoing termination requires explicit confirmation field; no generic status mass assignment |

The create_work_item variant resolves ticket client/default project and assignee
with the same checks as explicit task creation. It never silently creates project
or user. Responses never return unauthorized linked titles, user emails or notes.
No permission field, number, actor, version or audit timestamp is client-writable.

## State transitions and temporal semantics

Work: todo -> in_progress/blocked/cancelled; in_progress -> blocked/done/cancelled;
blocked -> todo/in_progress/cancelled; done -> in_progress (explicit reopen);
cancelled -> todo (manager restore). Initial ongoing work enters in_progress;
finishing it requires explicit end-of-operation, does not generate recurrence.
Leaving blocked clears current blocked reason but preserves history.

Ticket: new -> open; open -> pending_customer/pending_third_party/resolved;
pending states -> open/resolved; resolved -> closed/open; closed -> open only
by authorized reopen policy. Reopening creates a new SLA cycle with preserved
previous cycle. Closure/reopen authorization and configured grace period are
policy inputs, not hardcoded SLA promises. Idempotent same-state replay is not
a new transition/event. A public customer message can reopen under configured
policy; a private note cannot satisfy first response or customer communication.

Task deadline category order: completed/cancelled (report separately), ongoing,
no_due_date, overdue, due_soon (0..3 local days), on_track. Date-only overdue
starts at the following local midnight. Instant deadlines compare real instants.
No due date is fabricated from SLA, creation date or calendar views.

## My Work and analytics

Response items: `{kind: work_item|ticket, id, title, status, priority, due,
origin, linked_tickets: [{id,number,status}], version}`. Restrict related fields
to the caller's ACL. Tasks qualify through owner or explicit assignee membership;
tickets through assignee. ADR-0007 defines N:N suppression. Deduplication takes
place before cursor pagination across the full filtered authorized set.
Response also names `as_of`, timezone and applied filters. `unified_count`,
`ticket_count`, `work_item_count`, `active_no_due_date_count` and
`all_missing_deadline_count` have distinct meanings. Counts are optional on
paginated reads; when provided they use the same predicates/projection.

## Durable event contract

Envelope: event_id UUID, event_type allowlisted string, schema_version positive
integer, aggregate {type,id,version}, occurred_at UTC, actor {type,id nullable},
correlation_id, causation_id nullable, payload bounded typed object. Payload
uses IDs and transition information, not full email bodies or credentials.

Initial events: ticket.created/assigned/status_changed/message_received,
work_item.created/assigned/blocked/completed, sla.breached. Aggregate mutation
and envelope commit together. Consumer re-reads authoritative resource/scope
and never treats serialized actor as an unrestricted authorization grant.

`ticket.assigned` payload contains ticket_id, old_assignee_id nullable,
new_assignee_id, queue_id, client_id and aggregate version. Automation execution
records rule revision and source event. Stable logical effect key remains
`(rule_id, action_id, ticket_id)` across rule edits/reassign/reopen unless a
separate authorized new-work operation intentionally creates another task.
Each action has an immutable server-assigned UUID. Reordering preserves its
identity; deletion tombstones it; replacement creates a new UUID and requires
explicit review of new-work effects. Never reuse action IDs or infer identity
from position. Existing execution history retains the original rule revision.
Transport is at least once. Exactly-once claims refer only to protected business
effects, not Redis or SMTP delivery.
